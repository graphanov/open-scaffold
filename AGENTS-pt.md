# Instruções para agentes

Este projeto é [open-scaffold](https://github.com/graphanov/open-scaffold), um sistema operacional nativo de repositório e neutro quanto a runtime para desenvolvimento orquestrado por agentes. Ele vem com uma estrutura persistente de projeto — missão, roadmap, planos imutáveis, protocolos de emenda, decisões, evidências, pacotes de execução e práticas de passagem de sessão — para que qualquer agente ou orquestrador (Hermes, Claw/OpenClaw, Claude Code, Codex, Gemini ou similar) possa operar no repositório desde o commit #1 sem nova explicação.

## Layered architecture

open-scaffold tem várias camadas. O **sistema central** é uma disciplina de repositório independente de framework: missão, roadmap, planos, emendas, evidências, pacotes de execução, relatórios do operador e handover. **Orquestradores/agentes** como Hermes, Claw/OpenClaw, Claude Code, Codex e Gemini podem operar sobre esse substrato. **Runtime harnesses** como OMC e OMX estendem Claude Code/Codex com modos de workflow; eles não são equivalentes a orquestradores como Hermes ou Claw. Consulte `docs/OPEN_SCAFFOLD_SYSTEM.md` para a ontologia, `docs/TASK_RUN_MODEL.md` para a identidade de task/run/operator-surface, `docs/GITHUB_WORKFLOW.md` para a rastreabilidade de issue/PR/Codex-review e `docs/WORKFLOW.md` para orientação de fases.

## Project facts

- **Fonte de verdade da missão:** `MISSION.md` — objetivos, não objetivos e changelog de mudanças de escopo.
- **Fonte de direção do roadmap:** `ROADMAP.md` — marcos de produto/sistema e a cadeia de self-dogfood de item do roadmap para issue/task, plano, pacote de execução, PR e nota de release.
- **Ontologia do sistema:** `docs/OPEN_SCAFFOLD_SYSTEM.md` — mapa de fronteiras para o núcleo do Open Scaffold, orquestradores/agentes, runtime harnesses OMC/OMX, pontes de tarefas, superfícies de glass cockpit e GitHub.
- **Modelo de task/run:** `docs/TASK_RUN_MODEL.md` — `task_id` para trabalho durável, `run_id` para uma tentativa de execução, `question_id` para prompts ao operador e ids de chat/thread como vínculos opcionais.
- **Protocolo de fechamento de slice:** `docs/SLICE_CLOSE_PROTOCOL.md` — recibos de evidência, decisões pós-voo, força de aprovação, roteamento de correções e herança da próxima slice.
- **Protocolo de glass cockpit:** `docs/GLASS_COCKPIT_PROTOCOL.md` — vocabulário de eventos para status, bloqueios, perguntas, aprovações, recibos de evidência, links de PR e streams build-in-public.
- **Contrato de binding de runtime:** `docs/RUNTIME_BINDING_CONTRACT.md` — ciclo de vida/responsabilidades para bindings OMC/OMX/plain-agent/human que consomem pacotes de execução fora do núcleo.
- **Workflow do GitHub:** `docs/GITHUB_WORKFLOW.md` — rastreabilidade issue → task/run → branch/PR → CI/Codex review → aprovação humana → merge.
- **Diretório de planos:** `.osc/plans/` — arquivos de plano imutáveis organizados em subpastas de estágio (`active/`, `backlog/`, `done/`, `blocked/`), um por task/slice de feature, em conformidade com o esquema de 7 seções em `.osc/plans/handoff-template.md`. A pasta É o status — veja `.osc/plans/WORKFLOW.md` para as regras de movimentação.
- **Emendas:** novos aprendizados viram `<plan-slug>-amendment-<n>.md` na mesma pasta de estágio do plano pai, scaffolded por `osc amend <plan-slug> --message "<what changed>"` / `npx open-scaffold amend ...` ou pelo fallback de shell `./amend.sh <plan-slug>`. Planos nunca são editados no lugar; arquivos de emenda e o changelog de MISSION.md nunca são escritos manualmente.
- **Helpers de ciclo de vida:** prefira `osc amend <plan-slug> --message "<what changed>"` e `osc close <plan-slug> --message "<what shipped>"` para o caminho npm/day-two. Os fallbacks de shell continuam sendo `./amend.sh <plan-slug>` e `./close.sh <plan-slug>`; os scripts mantêm suas flags específicas, como `--stage` e `--backlog`.
- **Regras rápidas:** `.osc/RULES.md` — princípios compactos e inegociáveis. Releia antes de qualquer ação importante na estrutura do projeto.
- **Diretório de decisões:** `docs/decisions/README.md` — página pública de escolhas de design. Os registros ADR completos vivem internamente em `.osc-dev/decisions/` e não são distribuídos publicamente.
- **Notas de release / evidência:** `.osc/releases/` captura evidências de release nativas do scaffold para slices de produto significativas quando GitHub Releases são pesadas demais ou ainda não foram criadas. As notas devem citar item do roadmap, issue/task, plano, run ID, PR, verificação e trabalho de follow-up.
- **Workspace do owner:** `.osc-dev/` — ignorado pelo git; populado apenas ao trabalhar no próprio open-scaffold, não em templates clonados. Guarda todo o histórico de decisões em `plans/`, `decisions/`, `specs/` e `snapshots/`. **Antes de propor mudanças arquiteturais no próprio scaffold, leia `.osc-dev/plans/` e `.osc-dev/decisions/` primeiro** — muitas perguntas de design já foram investigadas lá. Ferramentas Grep/Glob pulam caminhos ignorados pelo git por padrão; inclua `.osc-dev/` explicitamente ao pesquisar.
- **Mapa de workflow:** `docs/WORKFLOW.md` — guia rápido de fase-para-ferramenta-para-comando.
- **Bootstrap:** `bootstrap.sh` — configuração idempotente opcional; cria diretórios lazy e carimba o changelog de MISSION.md.

## Operating rules

1. **Leia `MISSION.md` antes de sugerir ou escrever código.** Se ele contiver o marcador `<!-- mission:unset -->` ou o literal `TODO: define mission`, trate a missão como indefinida. Redirecione o usuário para definir a missão (via `./bootstrap.sh` ou edição direta) antes de prosseguir. O usuário pode substituir isso com uma instrução explícita para pular.
2. **Toda mudança não trivial deve rastrear para um arquivo de plano** em `.osc/plans/` que siga o esquema do template de handoff.
3. **Não edite planos no lugar.** Se novas informações mudarem o objetivo ou os critérios de aceitação de um plano, execute `osc amend <plan-slug> --message "<what changed>"` ou `./amend.sh <plan-slug>` — o helper autonumera o arquivo de emenda, scaffolds o esquema de 5 seções e carimba o changelog de MISSION.md. Preencha as seções `TODO:` que ele deixa. Nunca escreva arquivos de emenda manualmente, nunca edite manualmente o changelog de MISSION.md para emendas e nunca modifique o arquivo de plano pai.
4. **A verificação rastreia para critérios de aceitação.** Execute `./verify.sh` e qualquer verificação nativa de adapter contra os critérios de aceitação do plano, não contra vibes.
5. **Quando você "fica mais inteligente"** (chega nova informação que legitimamente muda o escopo), conduza o fluxo de emenda de forma conversacional: (a) pergunte ao usuário o que especificamente mudou e por quê, (b) resuma de volta na voz dele, (c) execute `osc amend <plan-slug> --message "<what changed>"` ou `./amend.sh <plan-slug>`, (d) preencha as seções `TODO:` do arquivo de emenda gerado com o resumo dele, (e) mostre o diff para revisão antes de stage. Não integre novos recursos silenciosamente; não recuse evolução legítima.
6. **Consulte `docs/WORKFLOW.md`** quando não tiver certeza de qual fase está ou qual ferramenta se encaixa na tarefa.
7. **Execute verificações de conformidade antes de mudanças de código não triviais.** Execute `./verify.sh --quick --quiet` e verifique o exit code. Em exit 0: prossiga silenciosamente (não mencione a verificação). Em exit 1: leia a saída de falha, bloqueie rigidamente e redirecione no primeiro check com falha. Os checks usam divulgação progressiva: o check da missão roda primeiro; o check de plano só ativa depois que a missão está definida. Se a missão estiver indefinida, redirecione para defini-la. Se a missão estiver definida mas não houver plano, redirecione para criar um. A flag `--quiet` suprime a saída em caso de sucesso, mas imprime detalhes de falha quando algo está errado. Se você não puder executar comandos de shell, verifique diretamente: primeiro confirme que `MISSION.md` não contém `<!-- mission:unset -->`; somente se a missão estiver definida, então verifique que `.osc/plans/` e suas subpastas de estágio (`active/`, `backlog/`, `done/`, `blocked/`) contêm pelo menos um arquivo de plano além do template.
8. **Detecte oportunidades de delegação nos planos.** Ao executar um plano de `.osc/plans/`, verifique se ele contém uma seção `## Execution strategy`. Se existir: leia os grupos paralelos e dependências, proponha paralelismo ao usuário (nomeie grupos e tarefas específicos) e avise se tarefas marcadas como paralelas compartilharem arquivos ou tiverem dependências não declaradas. Quando a execução precisar de OMC/OMX ou outro harness, crie ou solicite um pacote de execução vinculado (`osc run <plan> --task-id ... --executor ...`) em vez de tratar a thread de chat ou a sessão de runtime como estado canônico. Para mudanças de código/docs públicos, leve o mesmo rastro para o template de PR do GitHub e acione Codex review quando disponível. Se não existir, prossiga normalmente — a seção é opcional. Para setups sem agentes capazes, `./delegate.sh <plan-path>` gera prompts acionáveis de terminal a partir da seção Execution Strategy.

## Scope evolution protocol

Regras completas em `.osc/plans/README.md` (menos de 200 palavras). Resumo: planos são imutáveis; emendas se sobrepõem em ordem numérica; o changelog de MISSION.md registra cada pivot; agentes leem o plano original mais todas as emendas em ordem. **Emendas são scaffolded mecanicamente por `osc amend <plan-slug> --message "<what changed>"` ou `./amend.sh <plan-slug>`** — o helper autonumera o arquivo, escreve o esquema de 5 seções (Parent / Date / Learning / New direction / Impact on acceptance criteria) e carimba o changelog de MISSION.md. Agentes preenchem as seções `TODO:`; eles nunca escrevem arquivos de emenda manualmente nem editam MISSION.md para contabilidade de emendas.

## Verification marker convention

`MISSION.md` vem com `<!-- mission:unset -->` como marcador detectável por máquina de "missão ainda não definida". Ferramentas de verificação (comandos nativos de adapter, scripts customizados, revisores de código) devem tratar sua presença como bloqueador para qualquer trabalho que expanda escopo. open-scaffold define o marcador; ferramentas consumidoras decidem como honrá-lo.
