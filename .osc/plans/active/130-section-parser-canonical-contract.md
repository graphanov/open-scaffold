## Status

active

## Context

The independent-review deep interview (`.omc/runs/independent-review-slice-2026-05-29/DEEP_INTERVIEW_SPEC.md`, ambiguity 7%, posture A confirmed by owner) selected one executable first slice from five review themes: harden the hand-rolled Markdown section parser that anchors the plan lifecycle and converge its divergent siblings onto a single canonical contract. This continues the Milestone 11 "independent review hardening" lineage (`.osc/plans/done/012-independent-review-hardening.md`): turn an external review finding into a source-grounded, test-backed fix. Direct source reads on 2026-05-29 (and a consensus Architect/Critic pass) confirmed the defect is systemic duplication, not one regex: `splitSections` (`src/scaffold.ts:547`) has no fenced-code-block awareness, and at least five other heading-detection sites re-implement recognition and disagree with it on case, prefix-vs-exact matching, fence-awareness, and anchoring — `plan-validate.ts:144-149` (order re-parse) and `plan-validate.ts:33` (`lineNumberForHeading`), `validation.ts:42-44` (`hasHeading`, case-insensitive + raw interpolation), the `verify.sh:176-181` grep, and a CI-side Python detector in `.github/workflows/evidence-validate.yml`. This plan is planning-only and pending owner approval for execution (the execution gate from the spec is unchanged).

## Goal

Replace the regex-and-line-split section parser with a robust, still-dependency-free parser that ignores `##` lines inside fenced code blocks, and make `splitSections` the single section/heading authority that the named TypeScript callers and the `verify.sh` pre-flight consume — proven by a characterization corpus that pins both the current section maps and the current validation outcomes on every real plan and release note before any behavior changes.

## Implementation Architecture Coverage

- Strengthens: evaluation integrity and audit trails — the section parser is the substrate every plan/release-note validation reads, so a single correct contract makes acceptance-criteria checks trustworthy.
- Audit envelope: the implementing PR (two commits — characterization baseline first, behavior change second), the characterization corpus snapshot (current `splitSections` output AND current validation issue set over all `.osc/plans/**` and `.osc/releases/**`), and the new regression tests.
- Evaluation envelope: `npm test` (vitest), `npm run build:core` (`tsc -p tsconfig.json`), and `./verify.sh --strict` are the green gates; each acceptance criterion below maps to a named test or command.
- Feedback routing: a characterization diff that is not a provable, documented correction blocks the slice and routes to an amendment; any verify.sh regression on an existing plan routes to the AC5 contingency (document the divergence) rather than silently breaking the plan; a PR that combines the baseline and the behavior change in one commit is rejected at review (see AC6).
- Boundary: no runtime execution, MCP surface change, storage change, schema change, or new dependency — those stay out of this slice.

## Acceptance criteria

- [ ] **AC1 Code-fence safety:** a `## ...` line inside a fenced block (```` ``` ```` or `~~~`) is not treated as a section boundary. A regression test builds a plan whose `## Goal` body contains a fenced block with a `## Example` line and asserts the section map is unaffected.
- [ ] **AC2 Locked recognition contract (specified + tested):** the canonical rules are exactly — column-0 only (no leading whitespace; this is a *preserved* invariant, today's `/^##\s+(.+)$/` already requires column 0); exactly two `#` then ≥1 space/tab then non-empty text (also *preserved* — today's `^##\s+` already excludes `#`/`###`/`####` because the next char must be whitespace); optional trailing `#` run stripped (`## Goal ##` → `Goal`, additive/forward-looking); `trim()` + internal-whitespace-collapse; case-sensitive; and headings inside a fenced block are ignored. CRLF tolerated (including when detecting fences). Each rule has a test; the two preserved invariants are labelled as preserved so they do not register as "corrections" in the AC6 diff.
- [ ] **AC2b Fenced-block definition (specified + tested):** a fence opens on a column-0 line of 3+ backticks or 3+ tildes (info string allowed and never itself treated as a heading or as a close) and closes on the next column-0 line of ≥ the same count of the same character; backtick and tilde fences do not cross-close; an unterminated fence runs to end-of-document. Tests cover: open=3/close=4 closes, open=4/close=3 does not, a ```` ``` ```` line inside a `~~~` block is inert, and an info string containing `#`. 4-space indented code blocks are explicitly not tracked (named, deliberate divergence from CommonMark, documented in-code).
- [ ] **AC3 Single canonical contract with named convergence scope:** `splitSections` is the one authority. The converged set — and the only TS paths that must agree on a document's section map — is precisely: `splitSections` (authority), the `plan-validate.ts:144-149` order re-parse, `plan-validate.ts:33` `lineNumberForHeading`, and `validation.ts:42-44` `hasHeading` (as a presence probe per AC4). Explicit exceptions, each characterize-only this slice with a pinning test and a stated rationale: `updatePlanStatus` (`scaffold.ts:423`, a status-mutator regex, not a section-map parser) and `firstContentLine` (`plan-validate.ts:37`, outcome-inert line-number helper). `verify.sh` parity is handled by AC5; `delegate.sh` and the CI Python detector are deferred (Constraints). No detector outside this named set may silently disagree; any future divergence must be added here with rationale.
- [ ] **AC4 Interpolation safety + hasHeading semantics locked:** any dynamic heading match escapes user/schema-supplied heading text, so headings such as `Constraints / Out of scope` carry no regex-injection/metacharacter fragility. `hasHeading` keeps *prefix/startswith presence-probe* semantics against the canonical contract (it is a presence check, not a strict section-map key lookup), so `## Traceability chain` continues to satisfy `hasHeading(text, 'Traceability')`; the `validation.ts:134` `sections.get('Traceability') ?? sections.get('Traceability chain')` reconciliation is preserved as an asserted, comment-documented compatibility shim. A dedicated regression test pins `.osc/releases/2026-05-12-self-dogfood-release-loop.md` (`## Traceability chain`) as producing zero new `validateScaffold` warnings post-refactor.
- [ ] **AC5 verify.sh parity (decision locked = tighten):** `verify.sh:176-181` is tightened to a front-anchored, case-sensitive presence check keyed to the exact 8 `REQUIRED_PLAN_SECTIONS` names (drop the `.*` wildcard and the `-i` flag, so `## My Context Notes` no longer satisfies `Context`) and adds the omitted `Status` section so verify.sh and the TS layer agree on 8 sections. It stays presence-only and must not become stricter than `validatePlanFile` (order/emptiness/content authority remains the TS layer; `Constraints / Out of scope` is matched by its exact canonical name, not a stricter rule). An in-file comment records the intentional presence-only role. Contingent on the AC6 gate showing zero currently-passing plans regress under the new grep; the only fallback if the gate surprises is to document a specific lenient exception, never a silent divergence.
- [ ] **AC6 Characterization first (corpus-pinned, outcome-asserted, ordering-enforced):** before any behavior change, a characterization test captures (a) current `splitSections` section maps and (b) current validation outcomes — the issue set from `validateScaffold` over `.osc/releases/**` and `validatePlanFile` over `.osc/plans/**` — for every real document. The refactor proves: byte-identical section maps for every document with no fenced-heading / ATX-closed / case anomaly; for any document that does differ (the only corpus instance is `.osc/releases/2026-05-22-092-evolution-loop-visibility-v1.md`, whose fenced `## Acceptance criteria delta` key is dropped), the diff is a documented correction — a spurious key removed, never a real section lost; and **no validation outcome (pass/fail or issue set) changes for any existing plan or note**. Ordering is enforced: the baseline snapshot lands in a first commit that touches no parser logic, the behavior change lands in a subsequent commit reviewed as a diff against that committed baseline, and a reviewer rejects any PR that introduces both in one commit.
- [ ] **AC7 Green gates:** `npm test`, `npm run build:core` (`tsc -p tsconfig.json`), and `./verify.sh --strict` all pass.
- [ ] **AC8 Zero dependency delta:** `git diff -- package.json` adds no `dependencies` entry and no new runtime package appears in any lockfile.
