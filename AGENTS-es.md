# Instrucciones para agentes

Este proyecto es [open-scaffold](https://github.com/graphanov/open-scaffold), un sistema operativo nativo del repositorio y neutral respecto al runtime para desarrollo orquestado por agentes. Incluye una estructura de proyecto persistente — misión, hoja de ruta, planes inmutables, protocolos de enmienda, decisiones, evidencia, paquetes de ejecución y prácticas de traspaso de sesión — para que cualquier agente u orquestador (Hermes, Claw/OpenClaw, Claude Code, Codex, Gemini o similar) pueda operar en el repositorio desde el commit #1 sin que se le vuelva a explicar el contexto.

## Layered architecture

open-scaffold tiene varias capas. El **sistema central** es una disciplina de repositorio independiente del framework: misión, hoja de ruta, planes, enmiendas, evidencia, paquetes de ejecución, informes del operador y traspasos. **Orquestadores/agentes** como Hermes, Claw/OpenClaw, Claude Code, Codex y Gemini pueden operar sobre ese sustrato. **Arneses de runtime** como OMC y OMX amplían Claude Code/Codex con modos de flujo de trabajo; no son equivalentes a orquestadores como Hermes o Claw. Consulta `docs/OPEN_SCAFFOLD_SYSTEM.md` para la ontología, `docs/TASK_RUN_MODEL.md` para la identidad task/run/operator-surface, `docs/GITHUB_WORKFLOW.md` para la trazabilidad issue/PR/Codex-review y `docs/WORKFLOW.md` para la guía de fases.

## Project facts

- **Fuente de verdad de la misión:** `MISSION.md` — objetivos, no objetivos y registro de cambios de pivotes de alcance.
- **Fuente de dirección de la hoja de ruta:** `ROADMAP.md` — hitos de producto/sistema y la cadena self-dogfood desde el elemento de hoja de ruta hasta issue/task, plan, paquete de ejecución, PR y nota de lanzamiento.
- **Ontología del sistema:** `docs/OPEN_SCAFFOLD_SYSTEM.md` — mapa de límites para el núcleo de Open Scaffold, orquestadores/agentes, arneses de runtime OMC/OMX, puentes de tareas, superficies glass-cockpit y GitHub.
- **Modelo de tarea/ejecución:** `docs/TASK_RUN_MODEL.md` — `task_id` para trabajo duradero, `run_id` para un intento de ejecución, `question_id` para prompts del operador y chat/thread ids como enlaces opcionales.
- **Protocolo de cierre de slice:** `docs/SLICE_CLOSE_PROTOCOL.md` — recibos de evidencia, decisiones postflight, fuerza de aprobación, enrutamiento de correcciones y herencia del siguiente slice.
- **Protocolo glass cockpit:** `docs/GLASS_COCKPIT_PROTOCOL.md` — vocabulario de eventos para estado, bloqueadores, preguntas, aprobaciones, recibos de evidencia, enlaces de PR y streams build-in-public.
- **Contrato de enlace de runtime:** `docs/RUNTIME_BINDING_CONTRACT.md` — ciclo de vida/responsabilidades de enlaces OMC/OMX/plain-agent/human que consumen paquetes de ejecución fuera del núcleo.
- **Flujo de trabajo de GitHub:** `docs/GITHUB_WORKFLOW.md` — trazabilidad issue → task/run → branch/PR → CI/Codex review → human approval → merge.
- **Directorio de planes:** `.osc/plans/` — archivos de plan inmutables organizados en subcarpetas de etapa (`active/`, `backlog/`, `done/`, `blocked/`), uno por cada slice de task/feature, conforme al esquema de 7 secciones de `.osc/plans/handoff-template.md`. La carpeta ES el estado — consulta `.osc/plans/WORKFLOW.md` para las reglas de movimiento.
- **Enmiendas:** los nuevos aprendizajes se convierten en `<plan-slug>-amendment-<n>.md` en la misma carpeta de etapa que el plan padre, scaffolded por `osc amend <plan-slug> --message "<what changed>"` / `npx open-scaffold amend ...` o el reemplazo de shell `./amend.sh <plan-slug>`. Los planes nunca se editan in situ; los archivos de enmienda y el changelog de MISSION.md nunca se escriben a mano.
- **Helpers de ciclo de vida:** prefiere `osc amend <plan-slug> --message "<what changed>"` y `osc close <plan-slug> --message "<what shipped>"` para la ruta npm/day-two. Los reemplazos de shell siguen siendo `./amend.sh <plan-slug>` y `./close.sh <plan-slug>`; los scripts conservan sus flags específicos, como `--stage` y `--backlog`.
- **Reglas rápidas:** `.osc/RULES.md` — principios compactos no negociables. Vuelve a leerlo antes de cualquier acción importante sobre la estructura del proyecto.
- **Directorio de decisiones:** `docs/decisions/README.md` — página pública de decisiones de diseño. Los registros ADR completos viven internamente en `.osc-dev/decisions/` y no se publican.
- **Notas de lanzamiento / evidencia:** `.osc/releases/` captura evidencia de lanzamiento scaffold-native para slices de producto significativos cuando GitHub Releases es demasiado pesado o aún no se ha creado. Las notas deben citar elemento de hoja de ruta, issue/task, plan, run ID, PR, verificación y trabajo de seguimiento.
- **Espacio de trabajo del propietario:** `.osc-dev/` — gitignored; se completa solo al trabajar en open-scaffold en sí, no en plantillas clonadas. Contiene el historial completo de decisiones en `plans/`, `decisions/`, `specs/` y `snapshots/`. **Antes de proponer cambios arquitectónicos al scaffold en sí, lee primero `.osc-dev/plans/` y `.osc-dev/decisions/`** — muchas preguntas de diseño ya se investigaron allí. Las herramientas Grep/Glob omiten rutas gitignored de forma predeterminada; incluye `.osc-dev/` explícitamente al buscar.
- **Mapa de flujo de trabajo:** `docs/WORKFLOW.md` — hoja de referencia fase-a-herramienta-a-comando.
- **Bootstrap:** `bootstrap.sh` — configuración opcional e idempotente; crea lazy dirs y estampa el changelog de MISSION.md.

## Operating rules

1. **Lee `MISSION.md` antes de sugerir o escribir código.** Si contiene el marcador `<!-- mission:unset -->` o el literal `TODO: define mission`, trata la misión como no definida. Redirige al usuario para que defina su misión (mediante `./bootstrap.sh` o edición directa) antes de continuar. El usuario puede anular esto con una instrucción explícita de omitirlo.
2. **Todo cambio no trivial debe trazarse a un archivo de plan** en `.osc/plans/` que siga el esquema de la plantilla de handoff.
3. **No edites planes in situ.** Si nueva información cambia el objetivo o los criterios de aceptación de un plan, ejecuta `osc amend <plan-slug> --message "<what changed>"` o `./amend.sh <plan-slug>` — el helper autonumera el archivo de enmienda, scaffolda el esquema de 5 secciones y estampa el changelog de MISSION.md. Completa las secciones `TODO:` que deja. Nunca escribas archivos de enmienda a mano, nunca edites a mano el changelog de MISSION.md para enmiendas y nunca modifiques el archivo de plan padre.
4. **La verificación se traza a los criterios de aceptación.** Ejecuta `./verify.sh` y cualquier verificación nativa del adaptador contra los criterios de aceptación del plan, no por sensaciones.
5. **Cuando "te vuelvas más inteligente"** (llega nueva información que cambia legítimamente el alcance), conduce el flujo de enmienda de forma conversacional: (a) pregunta al usuario qué cambió específicamente y por qué, (b) resúmelo de vuelta con su propia voz, (c) ejecuta `osc amend <plan-slug> --message "<what changed>"` o `./amend.sh <plan-slug>`, (d) completa las secciones `TODO:` del archivo de enmienda generado con su resumen, (e) muéstrales el diff para revisión antes de staged. No integres nuevas funcionalidades en silencio; no rechaces una evolución legítima.
6. **Consulta `docs/WORKFLOW.md`** cuando no sepas en qué fase estás o qué herramienta encaja con la tarea.
7. **Ejecuta comprobaciones de cumplimiento antes de cambios de código no triviales.** Ejecuta `./verify.sh --quick --quiet` y revisa el exit code. Con exit 0: continúa en silencio (no menciones la verificación). Con exit 1: lee la salida de fallo, bloquea con firmeza y redirige en la primera comprobación fallida. Las comprobaciones usan divulgación progresiva: primero se ejecuta la comprobación de misión; la comprobación de plan solo se activa después de que la misión esté definida. Si la misión no está definida, redirige a definirla. Si la misión está definida pero no hay plan, redirige a crear uno. El flag `--quiet` suprime la salida en caso de éxito pero imprime detalles de fallo cuando algo va mal. Si no puedes ejecutar comandos de shell, comprueba directamente: primero verifica que `MISSION.md` no contiene `<!-- mission:unset -->`; solo si la misión está definida, comprueba que `.osc/plans/` y sus subcarpetas de etapa (`active/`, `backlog/`, `done/`, `blocked/`) contienen al menos un archivo de plan más allá de la plantilla.
8. **Detecta oportunidades de delegación en los planes.** Al ejecutar un plan de `.osc/plans/`, comprueba si contiene una sección `## Execution strategy`. Si existe: lee los grupos paralelos y dependencias, propón paralelismo al usuario (nombra grupos y tareas específicos) y advierte si las tareas marcadas como paralelas comparten archivos o tienen dependencias no declaradas. Cuando la ejecución necesite OMC/OMX u otro arnés, crea o solicita un paquete de ejecución enlazado (`osc run <plan> --task-id ... --executor ...`) en vez de tratar el hilo de chat o la sesión de runtime como canonical state. Para cambios de código/documentación pública, lleva la misma traza a la plantilla de PR de GitHub y activa Codex review cuando esté disponible. Si no existe, continúa normalmente — la sección es opcional. Para configuraciones sin agentes capaces, `./delegate.sh <plan-path>` genera prompts de terminal accionables a partir de la sección Execution Strategy.

## Scope evolution protocol

Reglas completas en `.osc/plans/README.md` (menos de 200 palabras). Resumen: los planes son inmutables; las enmiendas se superponen en orden numérico; el changelog de MISSION.md registra cada pivote; los agentes leen el plan original más todas las enmiendas en orden. **Las enmiendas se scaffoldean mecánicamente con `osc amend <plan-slug> --message "<what changed>"` o `./amend.sh <plan-slug>`** — el helper autonumera el archivo, escribe el esquema de 5 secciones (Parent / Date / Learning / New direction / Impact on acceptance criteria) y estampa el changelog de MISSION.md. Los agentes completan las secciones `TODO:`; nunca escriben archivos de enmienda a mano ni editan MISSION.md a mano para la contabilidad de enmiendas.

## Verification marker convention

`MISSION.md` se distribuye con `<!-- mission:unset -->` como marcador detectable por máquina de "misión aún no definida". Las herramientas de verificación (comandos nativos de adaptador, scripts personalizados, revisores de código) deben tratar su presencia como un bloqueador para cualquier trabajo que expanda el alcance. open-scaffold define el marcador; las herramientas consumidoras deciden cómo respetarlo.
